# 审核与续作证据优化

总入口见 [workflow-optimization](workflow-optimization.md)。

## 减少续作返回与审核文件

- `capture` 汇总首尾、拼接和字幕检查点。可确认帧号的零起点 H.264 MP4 使用一次解码提取多个检查帧，时间点贴近帧边界、时轴不适配或批量取帧异常时沿用逐点定位。每个检查点仍保有原尺寸证据和独立记录。中断后继续提取缺失文件。
- Fireplay 的准备、发布裁定和每次外部操作各自核对文件。单次操作内部共用已计算的文件哈希，后续操作重新核验。普通瑕疵按既有有界发布裁定继续，提交阶段核对同版证据及实时质量异议。

- 同一会话首次读取可运行 `work-packet RUN --checkpoint`，随后用 `work-packet RUN --since TOKEN`。每次重新核验当前状态，继续返回待办、任务、阻塞、费用与审核信息。内容哈希相同时省略知识导航和字幕时序诊断，变化时重发对应区块。阶段、状态、计划、候选或正式成片切换时重发完整工作包。新会话先取完整包。增量模式构造完整导航后计算差异。
- 工作包每次调用内按路径共用清单、质量记录、候选记录、定稿记录等解析结果。文件变化在下次调用时重新读取。知识检索和媒体证据门禁仍按各自依赖重新核验。
- `codex-packet RUN --context-references` 用路径与 SHA256 代替重复的规则正文。必要知识仍需实际读取，同一会话只有在已读且 SHA256 一致时才复用。图像、实际观察与审核要求沿用原规则。默认命令仍生成内嵌正文包。
- `poll RUN JOB1 JOB2` 一次检查多个已登记任务，每个真实任务分别查询并保存结果。单任务轮询和等待接口继续可用。批量查询遇到一个任务需要对账时，继续返回其他任务的状态。
- `batch-status ID --poll` 跨同一原片的语言 run 检查已登记的待处理模型任务，返回带 run 名的紧凑回执和需人工核对的异常列表。已完成且结果已收取的任务退出常规轮询。供应商依然按真实 ID 逐个查询，费用按原账本结算。
- 同一任务的新整幅对照优先复用已有的原尺寸 PNG。源媒体、帧号、解码版本与图片哈希均需匹配，再复用已发布证据文件。每个候选仍有独立清单与待审记录。
- 同一任务的计划输入按 SHA256 复用字节完全相同的冻结 JSON。各版本继续保留原有完整文件路径。现行可编辑输入独立保存，文件系统无法建立硬链接时复制并核验。

## 收益与验证

应减少重复脚本、相同音频的再次识别/分离/混音、完整模型的再次下载、未变片段的重复编码，以及重复手填路径/状态/哈希。首次复杂背景修复、译文润色和实际视听检查仍可能耗时；没有真实同素材对照，不能承诺“一小时降到多少分钟”。

执行回归位于 `tests/test_workflow_optimization.py` 和相关缓存测试；历史边界见 [维护摘要](history.md)。后续用 `timing RUN` 比较同等质量门禁下的首次运行、检查点恢复和局部修改，区分本地计算、供应商调用和未观测间隔；不把间隔统称 Codex 写文件时间。
