# 缓存与执行恢复

## 跨语种审核帧复用方案

同源立体声 WAV 在同一工作区、同一 Fireplay 需求（或本地制作范围）内按源哈希和 FFmpeg 解码配置复用。缓存索引只保存 run 和哈希，目标任务持有独立、可核验的文件。源缓存消失或不匹配时重新提取，目标语配音与混音继续独立执行。

本地 UVR 分离复用同一源音轨、模型权重、推理实现和引擎版本对应的已核验双音轨。同一需求中第二种及后续语言优先复用伴奏、人声 WAV；在申请重计算名额前查缓存，未命中才等待名额，取得名额后再次查缓存，分离结果缺失时才执行推理。缓存接入沿用原推理实现指纹，后续修改推理参数、输入处理或输出算法时须更新 `INFERENCE_IMPLEMENTATION`。制作工作包在 neutral/render 阶段列出同批次、同源且时间区间对应的已审批底片候选，通过 `reuse-neutral` 完整验证并绑定之后才进入制作。复用源任务的媒体与证据不撤销源任务的结案时钟。

台账仍采集全部实质事件，计时和运行事件目录改为一次目录扫描取得文件元数据。已入库且签名一致的文件不再重复解析。

1. **本轮实现整幅原片帧共享。** `capture` 原先只会检索当前 run 的整幅对照帧。同一原片的多个语种现在通过同一工作区的 `state/visual-decode-cache/whole-scene-source/` 查找匹配帧。索引只记帧号、证据路径和 SHA-256，按原片实际哈希、解码器版本和画面区域分组。Fireplay 还按需求 ID 隔离，本地制作使用独立命名空间。
2. **后续处理重复媒体。** 先列出同源 WAV、候选 MP4 和交付入口的相同哈希，再按存储合同将符合条件的不可变资产复用到各自路径。以完整包校验、可独立读取和清理依赖核对作为放行条件。
3. **工作包共用单次调用读到的导航记录。** `status`、`work-packet`、改进清单和知识反馈进度共用当前命令已读取的 JSON。原片检查将已验证的哈希交给调用者，省去紧接着的第二次整文件读取。每次调用重新读取当前记录并校验实际文件，正式计划校验继续独立执行。

新证据优先硬链接已匹配的无损帧，目标路径会核对哈希。文件缺失或哈希不同则重新解码相应帧，硬链接不可用时尝试经哈希核验的复制。各语种继续生成完整的证据目录、候选哈希、原定采样点和待观察项。索引发布使用短锁，写入失败时证据包仍能独立读取。首次并行遇到同源缓存缺失时，多个任务可能各解码一次。

验证在隔离目录复用既有原片和实际成片，只重新生成整幅审核证据。对照两组的证据文件哈希、采样点、源帧和候选帧抽取次数、耗时及硬链接去重后的磁盘占用。已有证据目录仍按各自清单核验。

`WOW-20261123-024` 的两条原片、16 份候选单次串行对照中，整幅审核证据耗时从 78.24 秒降到 63.49 秒，磁盘分配量减少 160.12 MiB。源帧抽取量从 190 张降到 87 张。由于各语种采样点并不完全重合，源片解码命令仍各执行了 16 次，只提取缺少的帧。两组各 412 个证据文件逐一哈希一致。计量覆盖整幅审核取证这一步，回执保存在本机 `work/state/program-optimization-phase4/wow-source-frame-benchmark.json`。

## 生成前复用与审核边界

新生成的 comparisons-v3 检查材料会先按实际素材哈希、解码器和处理代码版本、裁剪区域、实际帧号及图层标签查询缓存。未变化的图层直接从已校验的无损比较图中取回，不再启动对应的视频裁剪解码。原片时间戳和媒体信息也按内容与工具版本复用；变化的目标视频仍需取得实际时间戳并解码，不能仅凭“只改了四帧”的说明跳过新画面。

当一页所需的全部图层、帧号、区域和排列均与既有完整图片一致时，直接校验并复用整页，不再解压图片、拆分图层和重新拼图。只有部分图层相同时才走图层级复用。单纯避免视频解码不保证提速，实际素材的第一次图层缓存试验曾因 PNG 开销变慢，测试记录保留用于比较，不能把缓存命中率当作性能结论。

新目标视频的实际图层仍逐帧解码并计算包含尺寸的像素指纹；若它与旧页中对应图层像素完全一致，且其他所需图层也一致，可以直接复用旧页的图片字节，不再读取并拼接未变的源图层。任何一层像素不同才重新拼图。新页的素材哈希、实际帧号、PTS 和审核绑定仍来自新版本，像素相同不意味着复制旧通过结论。

部分图层复用使用单次操作内最多 32 MiB 的 RGB 图层内存缓存，重复字节不反复解压，达到上限即淘汰旧条目，不额外写图片。读取缓存图片前仍核对文件哈希；同一操作内已经证明相同的“像素指纹 + PNG 文件哈希”不重复解压校验，下一次操作重新核验，不用长期 mtime 信任代替内容校验。

缓存只增加 `state/visual-decode-cache/` 下的时间戳和图层定位 JSON，不另存全量帧或视频。新证据仍有自己的完整图片路径、全部原定帧、实际时间映射和 pending 审核模板。透明图层缓存的是原有灰底合成后的展示图层，保留原来的 alpha 呈现，不把透明图误当成不透明源素材。旧版本的观察、失败图片与审核状态均不修改。

文件不存在属于可重建缓存缺失，只解码缺少的帧；文件或索引校验失败则停止并保留现场。跨任务共享索引采用锁和原子合并；取证完成前再次核对输入没有改变。新证据不依赖旧目录才能打开，删掉旧目录也不能带走新证据的图片。

`visual-evidence` 返回并在新 manifest 中记录 `decode_reuse`：复用/新解码的图层帧数和时间戳缓存命中数。图层帧数是请求输出的唯一帧数，不等于编解码器内部实际扫描帧数。`pixel_storage` 区分硬链接、复制和新写入，并记录复制回退的错误编号；不能将缓存命中数直接当作磁盘节省量。

原片／底片／译片的原位去字三路取证也使用图层定位索引。按实际媒体哈希、代码版本、帧号及裁剪区域复用既有无损对照中的像素，仅对未命中的媒体帧执行分组稀疏解码。新证据保存独立的三路对照图及原有待审项。

诊断时可运行 `visual-evidence RUN --no-decode-cache`，对尚未生成的证据绑定禁用时间戳和图层解码缓存；已有完整不可变证据仍校验后复用，不覆盖旧审查。图片像素去重仍保留，参数不跳过任何质量门禁。旧证据不会为了升级而重写，首次遇到新的解码条件需要建立定位索引，后续才受益。

渲染检查点和片段缓存改为跟随明确的渲染模块集合及 Pillow 版本，不再因存储清理、报告或证据查看模块的独立变化而重新编码。源片、文字、时轴、绑定资产、字体及编码器变化仍参与原有失效判断。新增渲染依赖时必须更新 `render_cache.implementation_signature` 并补测试；该优化不放宽准备资产、质量异议或最终成片审核。

取证与两种交付模式的质检共用最近一份技术音检结果。缓存同时绑定源片和候选视频的实际哈希、音频策略、参考时长、实现和工具版本。首次或任何条件变更时做原有音频解码与判断，命中时使用原报告，包括已发现的失败。首尾实际听审、转写及口型检查仍按各自证据执行。

快速质检按实际源片哈希和 FFprobe 版本复用源片的完整解码帧数。同源多语种只需全量数一次源片帧，各语种实际候选仍执行原有完整解码、帧数、音频和质量检查。

当前未实现自动清理、跨 run 的通用渲染片段共享或任意修复脚本的局部增量执行。历史专用脚本仍可能整段重做；新图层缓存不意味着新目标视频可以免解码或免审查。
