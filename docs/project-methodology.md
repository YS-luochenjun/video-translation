# 项目方法论与知识闭环

本项目已形成可执行的方法论：先观察信息载体，按条件选择方法，以实际产物验证，在预算与返工边界内输出，再把有来源的经验送回下一次制作。Codex负责语义和质量判断，执行器负责媒体、模型任务、费用、状态与证据绑定。现行规则仍以[制作合同](../agent/contracts/workflow.md)、[知识合同](../agent/contracts/knowledge.md)和配置为准；本文解释整体关系。

## 从需求到交付

| 环节 | 核心判断 | 可复查结果 |
| --- | --- | --- |
| 承接与恢复 | 当前需求、所有原片/语种、已有聊天和账本是什么 | 请求版本、源哈希、授权、独立请求预算；unknown先核对 |
| 真实观察 | 信息主要靠人声、画面文案还是两者共同传递 | 按实例记录旁白/对白、文字区域与时间、运动/遮挡和疑点 |
| 按内容选路 | 哪个方法适用，何时换路或停止 | content_features与routing_assessment；首选、备选和实际理由 |
| 检索并冻结 | 政策、条件方法、同源案例分别支持什么 | context与plan冻结正文哈希；候选仅作风险提醒 |
| 制作与核验 | 译稿、声音、字层和底片能否共同成立 | 实际render/capture/review/quality，证据绑定成片哈希 |
| 有界收口 | 能否继续改善，是否达到预算或两轮返工边界 | 当前最佳完整译片；质量通过、带瑕疵输出及用户验收分别记录 |
| 提交与学习 | 平台实际受理了什么，下一次可复用什么 | 独立交付包、平台读回/绑定、候选/使用反馈和维护回执 |

默认[快速交付](../agent/workflows/fast-delivery.md)，必要时选严格路线。快速路线保留基本完整性和证据门禁。真实必需配音缺失必须明确报告。共享底片可以在核验后跨语言复用，新语言的定稿、配音、时轴、字层与成片审核各自建立。

选路依据见[三类信息载体](../knowledge/rules/content-led-localization-v1.md)和[方法选择](../knowledge/rules/agent-method-selection-v2.md)。简单底面、运动复杂底面、前景遮挡分别判断；固定模型不等于固定效果。模型API成功、技术检查通过、Agent自审、独立审核和用户验收各有自己的证据。

## 哪些经验才算被吸收

知识有三个出口：通用/条件方法进入rules及正式索引；源限定观察进入cases及同源索引；证据不足或假设仍保留candidate。失败、反例和“这次未使用”同样有价值，但不能伪装成算法成功。必要对照独立打包，不依赖可删除的任务目录。

`deliver/reflect`自动记录来源，Hook提炼触发条件、动作、失败签名、限制与下一次反证，`knowledge-review`决定合并、限定参考、待补证或历史保留。需要新方法或修订时先`knowledge-promote`，再绑定实际目标版本。完全处理后才能指纹归档原候选；部分采纳仍保留待办。制作通过`knowledge-use`反馈实际效果，反例返回修订队列。

“有候选文件”“已提纯”“正式检索可用”“实际使用有效”是四种状态。相同内容且scope一致才合并；同源十种语言或多轮返工仍然只有一个独立来源。旧失败、费用未知与原验收不被新总结覆盖。

## 查看当前状态

知识状态持续变化，不在方法论文档中累加“本轮已清零”的数字。历史整理快照见[维护历史](history.md)，当前值从以下入口取得：

```sh
# 使用doctor验证过的Python
python3 bin/va.py knowledge-queue
python3 bin/va.py hooks status
python3 bin/project_health.py
python3 bin/va.py knowledge-audit
```

队列中的候选、使用反馈、待补证事项分别处理；临时报告副本不算新经验。登记队列清零只说明当时已登记来源有明确出口，不能证明全部历史已穷尽，也不代表跨源、独立或母语验收通过。费用、质量和平台恢复待办保留在各自账本。

## 自动沉淀如何运转

交付/复盘自动记录来源，Agent在制作、修复、反馈结案时处理本次经验；独立经验任务处理全局增量。Fireplay巡检负责接入调度，存储任务负责保全后的整理。调度频率和宿主要求只在[三项定时职责](scheduled-tasks.md)维护，操作入口见[每日提纯](daily-knowledge-curation.md)和[知识技能](../.agents/skills/knowledge-curation/SKILL.md)。

`hooks status`同时显示`new_records`、`adoption_queue_open`和pending。没有新输入不代表旧候选已采纳；定时触发成功不代表审查成功。已有证据足以支持限定案例时先落地案例，将跨源复验作为扩大结论的条件；缺少当前必要证据则保持pending并记录具体补证动作。

在既有授权内自主完成审查、发布和归档，不依赖逐次提醒。公司偏好和质量标准的改变仍需对应明确确认。新记录持续产生，自动化负责推进这个闭环，不能把候选直接变成规则或消除未结费用。
