# 多原片并行制作

每需求保留一个编号负责聊天、原请求与原预算；默认将独立原片委派给制作子代理，原负责聊天同时推进另一条原片。用户已明确授权现在及后续这样分工，来源和并发上限在 [并行配置](../../config/fireplay-parallel.json)。主控巡检只向原负责聊天发送调度消息，制作子代理由原聊天创建和管理，不另建同需求的顶层负责聊天。只分派一层，子代理不得继续创建子代理。

## 接续与领取

1. 用doctor验证的Python执行 `fireplay-parallel plan CODE`。它只读原请求和分派记录，返回逐原片的稳定任务身份、源哈希、目标语、原预算及限定目录，不启动制作、付费或聊天。原片未下载校验、需求信息缺失、当前范围修订未审查时先定位对应缺口，不伪造新源登记。
2. 原负责聊天核对各原片的真实run、job/taskId、unknown费用和当前执行者。模型在途不等于可以重复提交；已完成的原片不再领取。旧现场已在推进的部分继续由原执行者处理，在明确检查点交接后才转派。新默认限制控制新领取，不杀掉已有模型任务。
3. 原负责人先对将要分派的原片执行 `fireplay-start`，建立实际members及绑定原预算，再用 `fireplay-parallel update CODE --spec FILE` 原子领取。owner在领取时记录自己，subagent领取先登记 `dispatch_unknown`，再调用宿主 `spawn_agent`。创建回执未知时查原代理状态，不重复spawn。实际返回agent ID后，用 `reconcile` 及真实创建回执文件绑定。只有领取成功才可执行；达到需求/全局上限时留队列，继续轮询和其他已领取工作，不为了抢名额无限重试。
4. 一个任务覆盖**一原片的实际全部目标语种**；同源语言共享清单和已审底片，但译稿、音轨、时间轴与审核逐语独立。原负责人也必须登记自己的领取，避免子代理与自己同时写同一原片。任务身份绑定UUID、内容版本、原片序号和SHA256；当前源或内容版本变化后旧任务不能作为新版本完成。

领取规格（值均取plan和真实宿主状态）：

```json
{"action":"claim","video_index":2,"owner_thread_id":"实际负责聊天ID","actor_id":"实际负责聊天ID","assignee_kind":"subagent","claim_token":"本次稳定唯一领取标识"}
```

后续规格使用领取返回的 `task_id`、`claim_token`、实际 `actor_id`。`reconcile` 追加实际 `assignee_id` 和 `evidence:["work/fireplay-monitor/真实创建回执.json"]`，回执须包含实际agent ID。`heartbeat` 续租；`block` 保存具体缺口和真实证据；`release` 需 `relinquish:true`、`work_stopped:true`、reason和证据，unknown派发还须 `reconciled_no_worker:true`，确认原执行者放弃写入后才释放；`complete` 需实际限定目录内的交付/审核证据，表示交回负责人，**不表示质量通过、平台提交或整项结案**。没有子代理工具或宿主并发名额时记录具体阻塞，可由原负责人在已领取范围继续，不假报已并行。

## 文件、费用与写入职责

- 共享记录由 `state/fireplay/parallel.json` 的全局锁维护；每次更新保留history。worker只写领取回执中的 `allowed_paths`，不修改兄弟原片、项目代码/config、全局知识/存储或其他需求。源文件只读。需要新run或独立制作脚本时先由负责人登记并重新取得限定范围，不能自行扩目录。
- 原负责人统一 `fireplay-start` 建立各源批次和语言run并绑定原预算。所有子代理禁止 `budget-open`、`budget-amend`、新建账本及直接外发付费模型；它们准备源绑定模型包，负责人串行处理本需求的付费提交与费用对账，再把真实taskId/结果交回。不同源可同时分析、观察、翻译、等待结果、制作及审核；本地重编码先由负责人排队，避免CPU/显存/磁盘争用。并行不是给每条原片再发一份额度。
- 原负责人统一修改request、登记回执、入库/共享/归属/绑定和completion-check/fireplay-close。子代理交接实际文件哈希、目标语覆盖、审核结论与限制、待办和所有模型任务引用；原负责人按真实发布审查及时提交可交版本，pending持续补齐。
- 租约过期只表示需要读取真实代理状态。运行中续租；idle/error也先核查在途任务、具体阻塞及原写入是否已停止。不得自动抢占、自动删记录、重发unknown模型或重建聊天。恢复使用同一任务身份/原代理，已释放后才可显式新领取。

## 监督与长期巡检

交付与领取分别收尾。负责聊天在 `fireplay-close` 后仍检查本需求的原领取；平台已绑定或请求已结案不会自动把领取改成 `worker_complete`。先用真实worker状态及交接记录确认已停止写入、在途任务已交代，再以原 `task_id`、`claim_token` 和允许目录内的当前哈希证据执行 `complete`。核对该任务状态和活跃原片计数的变化；具体操作回执留work/state。宿主暂时未加载历史worker、查不到ID或租约过期都不能证明已停止；缺证据保留具体阻塞，由原负责聊天核实，主控不改全局账本抢占名额。该步骤只交还写入职责，不改变原质量、费用或平台结论。

负责聊天在切换阶段、派发和恢复前读取 `fireplay-parallel status --code CODE`；全局主控读 `fireplay-parallel status`。新需求提示词自动带此流程。巡检发现多源积压时先读原负责聊天，再保存调度signal及真实发送回执，让原聊天领取/分派；已运行且已采用本政策的不重复催。跨需求仍遵守八需求上限、P0仅优先冲突资源、P1继续。并行来源上限与需求数是两层限制，不能用子代理绕过需求授权。

现有需求逐项接续，不批量覆盖request、chat或预算。正文新增原片是内容修订：保留原版本现场，沿原聊天明确审查；活动请求修订门禁不能通过手改JSON或子代理绕过。完成时仍核验全部当前原片×目标语的实际哈希、平台ID、共享、标签、归属和绑定。
