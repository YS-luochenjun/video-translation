# 后续质量反馈如何影响旧交付

文件可恢复、原评审曾通过、现在适合交付，是三个不同判断。用户的新反馈或可复现缺陷能够推翻视觉通过，但不应改写历史文件来掩盖误判。

1. 定位实际源、成片哈希和问题区间；保留用户原话、观察证据及绑定不确定性。
2. 使用 `agent/templates/quality-hold.json` 填写规格，执行 `bin/va.ps1 quality-hold SPEC`。规格和证据使用工作区相对路径；输入文件哈希必须匹配。共享底片本身有缺陷时另写一条 `asset_kind: neutral_master` 的记录，不能只标某一语言的成品。
3. 运行 `delivery-index` 刷新当前查看入口。历史manifest及评审不变；`library-find` 返回原status、当前effective_status、quality_holds、visual_reuse_holds和production_eligible。`availability=available`只说明包仍完整可恢复，不等于可用于制作。
4. 制作底片检查和deliver阻断有异议的实际哈希。即使修改旧批准布尔值、复制到另一个run、重新归档，仍无法用同一字节绕过。deliver也复核计划内底片，避免绕开正常render后交付新文件。
5. 修复版本使用新的字节和审核证据；新哈希不自动继承旧异议，也不自动通过。当前实现只追加阻断事件，不提供删除历史异议或一键重新批准原问题字节的入口。

记录及必要证据独立保存于 `knowledge/local/quality-holds/<源哈希>/<资产哈希>/`。清理run或交付库不会删除这些记录；完整迁移既有工作区时须携带knowledge/local。干净源码导出排除客户异议记录，通用反例和方法另存公开knowledge/examples，二者各司其职。单独旧交付包仍是历史快照，不能在丢失后续异议库后声称掌握最新验收状态。

记录具有来源、不可变事件ID和证据哈希。重复登记相同事件不重复累积；修改同一ID时报错，必要时追加新事件。记录缺失或被篡改时阻断当前用途，不静默恢复旧通过状态。

这个机制负责落实已经观察到的质量判断，不自动识别灰块、残字或错误运动。Agent仍须检查实际编码视频，分别报告自审、独立审查和用户验收。视觉缺陷不会自动否定已核验的声音、译稿或其他源素材。
