# 制作中的主动检查与有界改进

目标是减少可见编辑痕迹，同时在有限条件下完成整项交付。**内部质量判断、当前最佳完整输出、外部提交、方法有效性分别记录。** 普通瑕疵不能成为拖延、漏交或无限重试的理由，仍执行[最终输出](always-output.md)及现行[提交政策](../../config/fireplay-publication.json)。本流程不提高公司验收标准，不自动调用模型，也不自动修改方法。

## 触发与职责

Agent每次开始、恢复、换阶段先读 `work-packet RUN` 中的 `improvement_loop`。首次成片、返工成片、收到用户反例或重复失败时主动执行以下循环，无须用户提出同一个问题。没有新证据、不变的失败不反复开试验。实际调度仍依赖正在执行的Agent或已安装宿主任务；文件中的流程不是常驻后台。

1. **从观众问题倒查证据。** 先正常播放整片，完整听审，再比较原片与译片同一时刻。问“用户为什么会觉得直接贴字”“主体是否连同原字被抹去”“为什么结尾还有同一商标”“为什么少了一个语言”。从实际帧、音轨、清单和提交矩阵回答，不以API成功、漂亮缩略图或旧pass代答。
2. **主动寻找反例。** `capture RUN` 自动补充最多12组原生整幅画面对照，包含首尾、风险文字、时间轴和转场，返回 `review_probes.viewer`。查看整幅构图，再看文字原尺寸；清单外遗漏、邻近主体和片尾不能只靠裁剪文字审查发现。未选中的探针列在manifest，不声称全覆盖。静帧不能证明运动、声音或口型；沿既有基本检查/连续帧/音频合同补查。证据生成不会填pass。
3. **区分事实与解释。** 记录缺陷发生在什么时间、实例、语言和版本；根因先标hypothesis。有对照支持才标supported。特别写清“前一轮为什么漏检”，把缺失问题补进下一轮审查。常见层次分别是源解析漏项、译稿、底片修复、字形/排版、跟踪遮挡、音频时轴、编码或平台提交，不能统一归咎为模型不好。
4. **做最小有据修复。** 一轮改变一个主要变量，检查修改区域及一个未改区域；保留原版本，不覆盖失败记录。先用代表性困难片段检验共享方案，放行后每语言另审。卡住时依据证据比较至少两种可行方法（例如真实字体排版与ImageGen字层、ImageGen参考加Wan与连续局部修复）；选择/否决都写理由，不要求付费试完每一种。沿用原请求预算、未知费用和两轮返工上限，换方法、run或语言不能重置。
5. **前后验证再收口。** 同时检查内容、风格、主体、运动、声音和完整性。修复没有改善、产生反例或仍不确定都如实记录，不靠改分数证明成功。开发层发现状态/哈希/恢复错误时补会复现故障的回归测试；单条素材不为每个微小修复创建代码测试。
6. **留下可复用的防复发动作。** 有可验证的新修复或反例时按 `agent/templates/improvement-cycle.json` 填写run内规格，执行 `improvement-record RUN inputs/improvement.json`。必须有前/后两个实际视频哈希、前后证据、未改区域对照、漏检原因、下一次问题及限制。回执进入既有本地 `knowledge-queue`，证据独立保全；重复提交幂等。再按知识合同审查，只有同范围且证据足够才合并/发布。素材坐标和字体参数留在限定案例，下次通过 `knowledge-use` 记录实际效果；“记录了”不等于“推广了”或“有效了”。

## 决策分支

| 当前情况 | Agent下一步 | 对交付的影响 |
| --- | --- | --- |
| 缺实际观察或绑定过期 | 补当前版本证据，不能凭感觉签pass | 保持未审，不盲目重渲染或重付费 |
| 正常播放可接受，只有轻微差异 | 记录差异并完成既有审核 | 通过则直接deliver，不追逐像素一致 |
| 普通缺陷，有明确可改善变量且在边界内 | 最小修复，前后及未改区对照 | 不阻塞独立语种；继续推进完整交付矩阵 |
| 普通不合格，达到预算/返工/能力边界或没有有据改善 | finalize当前最佳**完整**译片，披露瑕疵，再按publication-review判断best_available | 内部revise保留；普通不合格可按政策提交 |
| 大面积撕裂、无法观看、严重主体损坏、漏译、必需配音缺失或有效质量异议 | 阻断对应版本，优先恢复既有可用版本或有界修复；缺口明确保留 | 不能把它称作可提交，也不能因此漏掉其他可交语言 |
| 一种语言失败/上传超时 | 保留原请求与已知ID，核查后有界恢复；继续其他语言 | partial仅中间状态，完整矩阵核验后整项结案 |

“其他语言能做成”只能说明共享链路可能可用，不能证明该语言没有缺字、断音或漏译。每语言仍以实际完整成片及回执判断。

## 怎样判断项目在进步

同源同语种前后证据可证明这一次的观察，不证明跨源普适。关注重复缺陷是否减少、漏检是否被提前发现、受影响区域是否改善、未改区域是否保持、是否减少返工及是否完整交付。时间用现有timing、费用用原账本、提交用completion-check；没有基准不编造提升百分比。用户后续指出问题时保留旧判断，并把反例回流；改进经验不回写旧验收。

经验任务继续只负责提纯/审查，存储任务只负责保全清理。不要为了“自我进化”让定时任务新增付费制作、自动平台回传、自动发布规则或自动commit/push。
